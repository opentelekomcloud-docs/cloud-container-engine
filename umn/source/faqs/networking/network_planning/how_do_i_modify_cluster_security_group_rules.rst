How Do I Modify Cluster Security Group Rules?
=============================================

CCE is a universal container platform. Its default security group rules apply to general use cases. When a cluster is created, a security group is automatically created for the master nodes and worker nodes, separately. The name of the master node security group is in the format of *{Cluster name}*\ **-cce-control-**\ *{Random ID}*, and that of the worker node security group is in the format of *{Cluster name}*\ **-cce-node-**\ *{Random ID}*. For CCE Turbo clusters, an additional network interface security group is created with the name format *{cluster-name}*\ **-cce-eni-**\ *{random-ID}*.

You can log in to the VPC console, choose **Access Control** > **Security Groups** in the navigation pane, and modify the security group rules for the cluster based on your security requirements.

You can check the default security group rules of clusters using different network models in:

-  :ref:`Security Group Rules in a Cluster That Uses the VPC Network Model <cce_faq_00265__section726682184019>`
-  :ref:`Security Group Rules in a Cluster That Uses the Tunnel Network Model <cce_faq_00265__section1427413563337>`
-  :ref:`Security Group Rules in a CCE Turbo Cluster That Uses the Cloud Native 2.0 Network Model <cce_faq_00265__section94793418319>`

.. caution::

   -  Modifying security group rules is a **high-risk operation** that **may impact cluster stability**. Proceed with caution and schedule changes during off-peak hours. Avoid modifying rules for ports essential to CCE operations. Note that some ports may also be used by your services. You are advised to **verify any modifications in a test environment** before applying them to production. The verification process should include **port connectivity, cluster component availability, and end-to-end service availability**. **Observe the system for a sufficient period of time** to avoid missing delayed faults caused by security group rule propagation delays and component reconnection timeouts. In particular, verify that persistent connections can be re-established normally after disconnection, and that new pods and nodes initialize correctly.
   -  When adding a security group rule, ensure that **this rule does not conflict with the existing rules**. If there is a conflict, existing rules may become invalid, affecting cluster running.
