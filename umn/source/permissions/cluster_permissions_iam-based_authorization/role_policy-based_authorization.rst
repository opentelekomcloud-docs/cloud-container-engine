Role/Policy-based Authorization
===============================

Role/Policy-based authorization provided by `Identity and Access Management (IAM) <https://docs.otc.t-systems.com/usermanual/iam/iam_01_0026.html>`__ lets you control access to CCE. With IAM, you can:

-  Create IAM users in your account for personnel based on your enterprise's organizational structure. Each IAM user has their own identity credentials for accessing CCE resources.
-  Grant users only the permissions required to perform a given task based on their job responsibilities.
-  Entrust an account or a cloud service to perform efficient O&M on your CCE resources.

If your account meets your permissions requirements, you can skip this section.

:ref:`Figure 1 <cce_10_0732__fig1351611812271>` shows the process of role/policy-based authorization.

.. caution::

   Cluster permissions apply only to cluster-related resources (such as clusters and nodes). To operate Kubernetes resources like workloads and Services, you must also be granted :ref:`namespace permissions <cce_10_0189>`.

Prerequisites
-------------

-  Only users with the **Security Administrator** role (which grants all IAM permissions except role switching), such as the default account owner, can view user groups and their permissions on the **Permissions** page of the CCE console.

   .. important::

      When using CCE as an IAM user, you must enable both programmatic access and management console access for that user.

#. `Log in as an IAM user <https://docs.otc.t-systems.com/usermanual/iam/iam_01_0032.html>`__ and verify permissions.

   In the authorized region, perform the following operations:

   -  In the service list, choose **Cloud Container Engine** to access the CCE console. Attempt to create a cluster. If the operation fails (assuming the user has only been granted **CCE ReadOnlyAccess**), the policy is in effect.
   -  In the service list, choose any service other than **Cloud Container Engine** (assuming the user has only been granted **CCE ReadOnlyAccess**). If an insufficient permissions message appears, the policy is in effect.

System Roles Supported by CCE
-----------------------------

Roles are a type of coarse-grained authorization mechanism that defines service-level permissions based on user responsibilities. Only a limited number of service-level roles are available for authorization. Roles are not ideal for fine-grained authorization and least privilege access.

The preset system role for CCE in IAM is **CCE Administrator**. When assigning this role to a user group, you must also select other roles and policies on which this role depends, such as **Tenant Guest**, **Server Administrator**, **ELB Administrator**, **OBS Administrator**, **SFS Administrator**, **SWR Admin**, and **APM FullAccess**.

System Policies Supported by CCE
--------------------------------

IAM provides two preset CCE system policies, **CCE FullAccess** and **CCE ReadOnlyAccess**.

-  **CCE FullAccess**: a system policy, which grants permissions for common operations on CCE cluster resources, excluding namespace permissions for clusters with Kubernetes RBAC enabled, as well as privileged administrator operations such as agency configuration and cluster certificate generation.
-  **CCE ReadOnlyAccess**: a system policy, which grants read-only permissions on CCE cluster resources, excluding namespace permissions for clusters with Kubernetes RBAC enabled.

.. note::

   **CCE Admin** and **CCE Viewer** are deprecated. Use **CCE FullAccess** and **CCE ReadOnlyAccess** instead.

Example Custom Policies
-----------------------

If the system-defined CCE policies do not meet your authorization requirements, you can create custom policies.

You can create custom policies using either of the following methods:

-  Visual editor: Select cloud services, actions, resources, and request conditions. No knowledge of policy syntax is required.
-  JSON: Create a JSON policy or edit an existing one.

This section provides examples of common custom CCE policies.

**CCE Custom Policy Examples**

-  Example 1: Creating a cluster

   .. code-block::

      {
          "Version": "1.1",
          "Statement": [
              {
                  "Effect": "Allow",
                  "Action": [
                      "cce:cluster:create"
                  ]
              }
          ]
      }

-  Example 2: Denying node deletion

   A Deny-only policy must be used in conjunction with other Allow policies. Otherwise, it has no effect. When a user is granted multiple statements for the same action, an explicit Deny overrides any Allow (**Deny takes precedence**).

   For example, to grant a user the **CCEFullAccess system** policy while preventing them from deleting nodes (**cce:node:delete**), create a custom policy with the same action but with the **Effect** set to **Deny**. Attach both policies to the user. Due to Deny precedence, the user can perform all CCE operations except deleting nodes. The following is an example of such a Deny policy:

   .. code-block::

      {
          "Version": "1.1",
          "Statement": [
              {
                  "Effect": "Deny",
                  "Action": [
                      "cce:node:delete"
                  ]
              }
          ]
      }

-  Example 3: Creating a custom policy containing multiple actions

   A custom policy can contain actions from multiple services. Ensure these services are of the same scope, either project-level or global. The following is an example policy containing multiple actions:

   .. code-block::

      {
          "Version": "1.1",
          "Statement": [
              {
                  "Action": [
                      "ecs:cloudServers:resize",
                      "ecs:cloudServers:delete",
                      "ecs:cloudServers:delete",
                      "ims:images:list",
                      "ims:serverImages:create"
                  ],
                  "Effect": "Allow"
              }
          ]
      }

CCE Resources
-------------

A resource is an object managed by a service. CCE supports cluster-scoped authorization. When creating a policy, specify a resource path to restrict access to specific resources.

.. table:: **Table 3** CCE resources and their paths

   +-----------------------+-----------------------+------------------------------------------------------------------------------------------------------+
   | Resource              | Resource Name         | Path                                                                                                 |
   +=======================+=======================+======================================================================================================+
   | cluster               | Cluster               | Format:                                                                                              |
   |                       |                       |                                                                                                      |
   |                       |                       | *CCE:*:*:cluster:cluster_name*                                                                       |
   |                       |                       |                                                                                                      |
   |                       |                       | The first \* is the region ID, and the second \* is the domain ID.                                   |
   |                       |                       |                                                                                                      |
   |                       |                       | Note:                                                                                                |
   |                       |                       |                                                                                                      |
   |                       |                       | For cluster resources, IAM automatically generates the prefix *CCE:*:*:cluster:* for resource paths. |
   |                       |                       |                                                                                                      |
   |                       |                       | Use a cluster name to specify a resource path. The wildcard (``*``) is supported. Example:           |
   |                       |                       |                                                                                                      |
   |                       |                       | *CCE:*:*:cluster:\**: any cluster                                                                    |
   |                       |                       |                                                                                                      |
   |                       |                       | *CCE:*:*:cluster:test*: a cluster named **test**                                                     |
   +-----------------------+-----------------------+------------------------------------------------------------------------------------------------------+

Example: Forbid users from deleting cluster nodes that match a specific naming pattern, for example, nodes in clusters whose names start with **test**.

.. code-block::

   {
       "Version": "1.1",
       "Statement": [
           {
               "Effect": "Deny",
               "Action": [
                   "cce:node:delete"
               ],
               "Resource": [
                   "CCE:*:*:cluster:test*"
               ]
           }
       ]
   }
